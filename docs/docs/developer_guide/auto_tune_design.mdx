## 1. Motivation

Getting good performance out of SGLang today means hand-tuning two layers that
interact:

- **Kernels and their dispatch.** SGLang has several backends for MoE (triton,
  cutlass, ...), attention, GEMM, and allreduce, and most of them have their
  own tunables — tile sizes in the triton fused MoE, cutlass kernel variants,
  the batch-size thresholds that pick one backend over another. Each is tuned
  by a separate script (`benchmark/kernels/**/tuning_*.py`) that a human runs
  per model, per parallelism, per GPU, and whose output lands in a checked-in
  config directory.
- **Deployment flags.** `tp_size` / `dp_size` / `ep_size`, attention and MoE
  backend selection, `chunked_prefill_size`, `mem_fraction_static`,
  `max_running_requests`, CUDA graph batch sizes, speculative decoding shapes,
  chosen for a model, GPU, and workload.

That knowledge lives in cookbook recipes, tribal experience, and one-off sweeps.
When a model, a kernel, or a GPU generation changes, it silently goes stale.

We want a first-class **auto-tune framework** with one command at the top:

```bash
python -m sglang.auto_tune --model-path Qwen/Qwen3-30B-A3B-Instruct-2507 --tp 8
```

Given a model and a parallelism it tunes every kernel the model uses on this
platform, picks backends and dispatch heuristics, and can go on to search the
deployment flags under a workload and SLA. Every one of those is the same
loop — a search space, a strategy, a measurement, an objective — so they share
one framework, and a contributor extends it with a new knob family, strategy,
objective, or execution backend without touching the loop.

## 2. Starting position

Kernel tuning exists as one script per kernel (`benchmark/kernels/**/tuning_*.py`),
each with its own search loop, worker pool, and output format; there is **no
shared framework and no server-level tuning tool in tree today**. An earlier YAML-driven
`sglang.auto_benchmark` existed and was removed in
`075bd97952 [Benchmark] Remove obsolete auto-benchmark remnants (#31941)`.
This design is therefore greenfield, with no compatibility burden — but the
removed tool is worth reading once (`git show 075bd97952^:python/sglang/auto_benchmark_lib.py`)
because its failure modes are the ones this design is shaped to avoid (§2.2).

### 2.1 What we build on

| Piece | Location | Role for auto-tune |
| --- | --- | --- |
| Serving benchmark | `python/sglang/benchmark/serving.py` | `run_benchmark()`, `BenchmarkMetrics`, `wait_for_endpoint()` — the measurement client. Do not fork it. `run_benchmark()` writes a module-global `args`, so concurrent trials must run their client in separate processes. `success_rate` is not a `BenchmarkMetrics` field; the driver derives it from `completed / num_prompts`. |
| Offline throughput | `python/sglang/benchmark/offline_throughput.py` | Second measurement modality (no HTTP server) |
| Steady-state metrics | `python/sglang/benchmark/steady_state.py`, `steady_state_serving.py` | Interval selection that excludes ramp-up/drain — the right window to *tune* against. `serving.py` does not call it; `steady_state_serving.run_steady_state_benchmark()` is the entry point that wraps a run and returns both full-run and steady-state metrics. |
| Datasets | `python/sglang/benchmark/datasets/` | Workload materialization |
| Endpoint helpers | `python/sglang/benchmark/endpoint.py` | Base-URL resolution, IPv6-safe |
| Server args | `python/sglang/srt/server_args.py`, `server_args_config_parser.py` | Knob metadata source, and the `--config` loader that consumes our output |
| CI stub | `.github/workflows/auto-tune.yml` | Currently a placeholder job; the eventual home for scheduled tuning |
| Heuristic tuner | `python/sglang/multimodal_gen/runtime/server_args/auto_tune.py` | Prior art: zero-measurement `performance_mode` presets, useful as search *seeds* |
| Kernel tuners | `benchmark/kernels/fused_moe_triton/tuning_fused_moe_triton.py` and siblings, `srt/model_executor/runner/flashinfer_autotune.py` | The inner layer's drivers. The MoE script already derives shapes from `(model, tp, ep, dtype)`, sweeps a batch-size list, and runs a ray worker pool; it becomes a kernel driver + space + reporter rather than being rewritten. Its output directory (`moe_runner/triton_utils/configs/`) is the deployable artifact. |

`steady_state.py` deserves special mention: measuring a tuning candidate over
its full run mixes in ramp-up and drain, and two configs that differ only in how
fast they reach steady state get ranked on the transient rather than on the
throughput you will actually operate at.

### 2.2 Lessons from the removed tool

Recorded because these are the specific mistakes the abstractions in §4–§6 exist
to prevent, not as criticism of a tool that served its purpose:

1. **Every policy was hard-coded in one module.** Search, objective, SLA check,
   execution, and reporting were module-level functions wired by one driver
   loop. Adding a search strategy meant adding an `elif tier == 4`.
2. **The search was a truncated grid over YAML key order.** Which candidates
   survived a `max_candidates` cutoff depended on dict ordering in the config —
   so the result was sensitive to something the user had no reason to think
   was meaningful.
3. **The SLA check silently under-enforced.** It read only mean TTFT/TPOT, while
   the shipped configs specified p99 thresholds and a success-rate floor. Those
   keys parsed fine and were ignored, so every candidate "passed" and ranking
   degenerated to raw throughput.
4. **One trial at a time.** No use of a multi-GPU host for concurrent small-model
   trials, and no multi-node candidates at all.
5. **Results were not deployable.** The output was a Markdown table and a
   rendered command string; nothing emitted a config the runtime could load.

Lesson 3 is the important one: a tuning tool that reports a confident winner
under a constraint it never actually enforced is worse than no tool.

## 3. Goals / non-goals

**Goals**

- G1. One declarative config describes *what to tune, on what workload, under
  what constraint* — not *how to search*.
- G2. Every policy is a pluggable, registered component: space, strategy,
  executor, driver, objective, constraint, store, reporter.
- G3. Bounded and interruptible: hard wall-clock budget, per-trial timeouts,
  resumable, safe to Ctrl-C, no orphaned server processes.
- G4. Trustworthy results: deterministic trial keys, recorded environment
  provenance, failures kept with a diagnosis rather than dropped.
- G5. Deployable output: whatever the tuned layer consumes directly — a kernel
  config file, a dispatch table, or a `ServerArgs` YAML — never a table a human
  retypes.
- G6. Reuse existing measurement code (`benchmark/kernels/**`,
  `sglang.benchmark`) as drivers rather than forking it.
- G7. Two layers, one framework: kernel tuning is the inner layer, deployment
  tuning the outer, and they compose (§9.3).

**Non-goals (v1)**

- Not online/runtime adaptation. Tuning is offline; adaptive speculative
  decoding and elastic EP are separate mechanisms.
- Not a cross-framework comparison tool. Comparing against vLLM / TensorRT-LLM
  is a separate workflow that can consume this framework for its SGLang leg.
- Not an accuracy tuner. Correctness is a pass/fail constraint, never an
  objective.

## 4. Core concepts

```
Task        = Model + Hardware + Workload + Objective + Constraints + Budget
Space       = named knobs -> domains (+ conditionals, + feasibility rules)
Point       = one concrete assignment of knobs (a tile config, a backend
              choice, a candidate deployment)
Bucket      = the result partition a trial competes in ("" = one winner;
              "batch_size=64" = one winner per shape)
Trial       = (Point, Workload, Load, Fidelity, Bucket) executed once -> Measurement
Measurement = metrics + status + artifacts (logs, bench output, provenance)
Strategy    = f(history) -> next batch of Points   (ask/tell)
Executor    = where and how many trials run at once
Driver      = how one trial is launched and measured
Objective   = f(Measurement) -> score              (scalar or vector)
              + aggregate(all Measurements of a Point) -> point score
Constraint  = f(Measurement) -> feasible?          (SLA, accuracy, memory)
Store       = durable trial log + resume + dedup
Reporter    = TuneResult -> artifacts
```

The central loop is deliberately boring:

```python
while not budget.exhausted():
    for point in strategy.ask(n=executor.free_slots):
        for trial in trials_for(point):               # one per workload x load
            executor.submit(trial, timeout_s=budget.remaining_seconds(),
                            prune_check=strategy.should_prune)
    for measurement in executor.drain():
        store.record(measurement)
        strategy.tell(measurement)
ranking = rank_by_bucket(store.history())            # per bucket, one entry per Point
reporter.emit(result)
```

Everything interesting is in the pluggable pieces.

Ranking is per **point**, not per measurement: a point is measured once per
(workload, load), `best.yaml` needs exactly one winner, and a point is feasible
only if every one of its measurements is. `Objective.aggregate()` is the hook
that turns a point's measurements into one score. The v1 default handles the
single-measurement case and returns "unrankable" otherwise, so a multi-workload
config fails loudly until an aggregating objective is supplied (§15). Only
full-fidelity measurements enter the ranking; reduced-fidelity rungs are a
strategy's private signal.

Ranking is also per **bucket**. `TuneTask.bucket_of(workload, load)` names the
partition a trial competes in. Deployment tuning uses one shared bucket and gets
one `best.yaml`. Kernel tuning buckets by shape or batch size and gets one
winner per bucket — which is exactly the per-shape config file a kernel reads,
or the batch-size thresholds a dispatch heuristic needs. `best.yaml` is the
one-bucket special case, not a separate code path.

## 6. Extension points

All plugins register by name; the config selects them by name. Out-of-tree
plugins register by importing their module.

```python
from sglang.autotune.registry import register_strategy
from sglang.autotune.strategy.base import Strategy

@register_strategy("coordinate")
class CoordinateDescent(Strategy):
    def ask(self, n): ...
    def tell(self, measurement): ...
```

| Extension point | Contract | Ship in v1 | Why you would add one |
| --- | --- | --- | --- |
| `Space` | `knobs()`, `feasible()` | `server_args`, presets | New subsystem knobs (PD, HiCache, elastic EP) |
| `Strategy` | `ask` / `tell`, optional `should_prune` | `grid`, `random`, `coordinate`, `asha` | Bayesian/Optuna, cost-aware search |
| `Executor` | `submit(trial, timeout_s, prune_check)` / `drain`; every submission yields one measurement, cancelled ones as `CANCELLED` | `serial`, `pool` | Slurm, k8s, multi-node PD topologies |
| `MeasurementDriver` | `measure(trial, slot, timeout_s, prune_check)`; may attach `Measurement.discovered` for sweep-in-one-call tools | `moe_triton`, `serving`, `offline` | cutlass profiler, allreduce, attention microbench, RL loop, multimodal |
| `Objective` | `components()` per measurement, `aggregate()` per point | `scalar`, Pareto | Multi-workload aggregation, custom scalarization, cost per token |
| `Constraint` | `check()` | `MetricThreshold` | Per-tenant SLOs, accuracy gates |
| `TrialStore` | `record` / `history` | `jsonl` | Shared team DB, W&B, MLflow |
| `Reporter` | `emit()` | `markdown`, `csv`, `best_config` | Dashboards, PR comments |

**Knobs come from `ServerArgs`, not a hand-maintained list.** `ServerArgs` is a
dataclass whose fields carry `Annotated[..., Arg(...)]` metadata, and
`arg_groups/arg_utils.py::add_cli_args_from_dataclass` builds the parser from
it. The `server_args` space reads that same field metadata — type, choices,
default, `cli_name`, `no_cli` — rather than the argparse `_actions` it produces,
so the coupling is to a declared contract and not to parser internals. The few
flags with dynamic choices (`--reasoning-parser`, `--tool-call-parser`) are
added to the parser by hand and need the same by-hand treatment here. That
removes the need for an alias table
(`tp` vs `tp_size`), catches a typo'd flag at config-load time instead of twenty
minutes into a run, and makes new flags tunable the day they land. Curated knob
*families* (`attention`, `memory`, `moe_ep`, `speculative`, `scheduler`) sit on
top, because "which flags are worth tuning" is judgment, not metadata.

**Feasibility rules live with their owners.** Each space contributes predicates —
"fa3 requires sm80+", "`ep_size` must divide `tp_size * dp_size`",
"`speculative_*` requires a draft model" — so infeasible points are rejected
before a GPU is allocated, rather than accumulating in the tuner as a table of
special cases.

## 7. Config schema

```yaml
schema_version: 1
name: glm-4.6-8xh200-chat

model:
  path: zai-org/GLM-4.6
  trust_remote_code: true

hardware:
  gpu_count: 8
  gpus_per_trial: 8          # 8 -> 1 concurrent trial; 1 -> 8 concurrent trials

workload:
  - name: chat
    kind: random
    num_prompts: 200
    input_len: 1000
    output_len: 1000
  - name: summarization
    kind: random
    input_len: 8000
    output_len: 1000

measure:
  driver: serving
  endpoint: /v1/completions
  steady_state: true         # rank on the steady-state window, not the full run
  load:
    # exactly one of `fixed` or `search`
    # fixed: [{max_concurrency: 4}, {max_concurrency: 8}, {}]   # {} = unbounded
    search:                  # capacity search: highest qps that meets constraints
      qps: {lower: 0.25, upper: 4.0, tolerance: 0.1, max_rounds: 5}
      max_concurrency: 64
  warmup_requests: 32

objective:
  maximize: output_throughput

constraints:
  - {metric: p99_ttft_ms, max: 1500}
  - {metric: p99_tpot_ms, max: 30}
  - {metric: success_rate, min: 0.99}

space:
  fixed:
    mem_fraction_static: 0.82
    schedule_policy: lpm
  presets: [attention, scheduler]
  knobs:
    tp_size: [8]
    ep_size: [1, 4, 8]
    chunked_prefill_size: [4096, 8192]
    max_running_requests: [32, 48, 64]
    prefill_attention_backend: [fa3, flashinfer]   # overrides the same knob in a preset
    decode_attention_backend: [fa3, flashinfer]
    speculative_algorithm: [null, EAGLE]
  conditional:
    - when: {speculative_algorithm: EAGLE}         # only sampled when the base knob matches
      knobs:
        speculative_num_steps: [3, 5]
        speculative_eagle_topk: [4, 8]

search:
  strategy: asha
  max_trials: 40             # measurements, not points: 2 workloads -> 20 points
  budget_hours: 12
  resume: true
  seed: 1

output:
  dir: ./autotune/glm-4.6-8xh200-chat
  reporters: [markdown, csv, best_config]
```

Two properties the schema is designed to guarantee: a `max_trials` cutoff never
turns knob *ordering* into a hidden sampling rule (only `coordinate` reads
declaration order, and it does so on purpose: the baseline is each knob's first
value and the sweep follows that order), and every `constraints` entry is
checked against a metric the driver declares it can emit, so a threshold can
never be silently ignored. Explicit `knobs` override a knob of the same name
contributed by a `presets` entry.

## 8. Search strategies

One trial costs minutes — model load, warmup, benchmark run — so the strategy
layer's job is to spend a fixed trial budget well.

| Strategy | When to use | Sketch |
| --- | --- | --- |
| `grid` | Small spaces, exhaustive answers | Full product over the feasible set |
| `random` | Baseline, more than ~5 knobs | Uniform sample, deduped |
| `coordinate` | Improving a config you already run | Start at the `fixed` baseline, sweep one knob at a time, keep winners, repeat until no gain |
| `asha` | Cold start with a real budget | Cheap rung first (fewer prompts), promote the top fraction to full runs |

Two cross-cutting mechanisms available to any strategy:

- **Multi-fidelity.** A trial can run reduced (fewer prompts, one workload
  slice). `Fidelity.level` 0 is full; higher levels are cheaper rungs, and
  `level`, `scale`, and `repeats` are all part of the trial key. ASHA uses
  rungs for promotion only: reduced-fidelity measurements never enter the final
  ranking, so a winner is always a full-run winner. The QPS capacity search is
  a per-point inner loop in the driver rather than a strategy concern, since it
  characterizes one config rather than exploring the space.
- **Incumbent pruning.** If partial metrics already violate a constraint, abort
  and record `PRUNED` rather than paying for the full run. Strategies opt in via
  `should_prune()`; the default never prunes.

Recommended defaults: `asha` for a cold start, `coordinate` when the config
supplies a non-trivial `space.fixed` baseline.

## 9. Execution

### 9.1 Serving driver

Launch `python -m sglang.launch_server`, poll with
`benchmark.serving.wait_for_endpoint`, drive load with
`benchmark.serving.run_benchmark`, tear down. Hardening the framework requires:

- one process group per trial with guaranteed teardown on timeout and SIGINT —
  an orphaned server holding a port and 80 GB of HBM poisons every later trial;
- per-trial timeout derived from the *remaining budget*, not a constant — the
  orchestrator passes it on every `submit()`, and the executor forwards it to
  `measure()` unchanged;
- structured failure classification (OOM / port in use / unsupported flag /
  model load / crash / health timeout) recorded on the trial, so a report can
  say "6 of 24 candidates OOMed" instead of "6 failed";
- provenance capture — git SHA, `sglang.version`, torch/CUDA/driver, GPU model,
  relevant `SGLANG_*` env vars with secrets scrubbed.

### 9.2 Pool executor

Partitions `gpu_count` into `gpu_count // gpus_per_trial` slots and runs that
many trials concurrently, each pinned via `CUDA_VISIBLE_DEVICES` with its own
port. This is the largest wall-clock win available for small-model tuning — eight
1-GPU trials on an 8-GPU host — and needs only slot and port bookkeeping, which
is why `TrialSlot` is a first-class type. Multi-node executors (PD topologies,
cross-node EP) are a later extension behind the same `Executor` protocol.

### 9.3 Kernel drivers and the two-layer composition

A kernel driver is a `MeasurementDriver` that never starts a server: `measure()`
runs a microbenchmark of one point and returns `{"latency_us": ...}`. The rest
of the framework is unchanged, and it fits better than serving does — the space
is small and structured, measurements are deterministic and take seconds, and
the executor is the multi-GPU worker pool the tuning scripts already have.

| Kernel | Space | Bucket | Driver wraps | Output |
| --- | --- | --- | --- | --- |
| triton fused MoE | `BLOCK_SIZE_M/N/K`, `GROUP_SIZE_M`, `num_warps`, `num_stages` | batch size | `benchmark/kernels/fused_moe_triton/tuning_fused_moe_triton.py` | per-shape JSON under `moe_runner/triton_utils/configs/` |
| cutlass GEMM | kernel variant list | (M, N, K) | cutlass profiler; one call sweeps every variant, returned via `Measurement.discovered` | kernel selection table |
| allreduce | `{custom, nccl, nccl_symm, torch_symm}` | message size | allreduce microbench | dispatch thresholds |
| attention / MoE runner backend | backend choice | (batch, seq_len) | per-backend microbench | dispatch thresholds |
| speculative decoding | `num_steps`, `topk`, `num_draft_tokens` | batch size | serving or offline driver, decode-only workload | per-batch-size table |

The space derives its shapes from the model the way the existing scripts do:
`(model, tp, ep, dtype)` gives `num_experts`, `topk`, `hidden_size`,
`shard_intermediate_size`, `block_shape`, and a default batch-size list. Shape
derivation belongs to the kernel's space, not to the framework.

**Layering.** Kernel configs depend on parallelism; deployment tuning changes
parallelism. So the order is fixed: the outer task pins `tp` / `ep`, the inner
kernel tasks run for that parallelism and their outputs are cached by
provenance, and only then are backend and scheduler knobs searched under a
workload. `sglang.auto_tune --model-path X --tp N` is the inner layer alone;
`sglang.autotune run --config tune.yaml` can invoke it as a pre-trial step per
distinct parallelism it visits. Backend *selection* (attention, MoE runner,
allreduce) is cheaper and less noisy in the inner layer, so that is where it
defaults to; the outer layer re-checks it end-to-end only when asked.

### 9.4 Optional plugin surfaces

- **Heuristic seeding.** `multimodal_gen/runtime/server_args/auto_tune.py` shows
  the value of zero-measurement presets; `space.presets` can seed the first
  candidate from such heuristics rather than an arbitrary baseline.

## 10. State, resume, and reproducibility

- **Trial key** = hash of (normalized point, workload, load, fidelity,
  provenance fingerprint). Deterministic and order-independent.
- **Store** appends every trial — including failures — as it completes, so an
  interrupted run resumes having lost at most one trial.
- **Provenance is part of the key.** Results are reused only when code,
  hardware, and workload match. Reusing a measurement from before a kernel
  change is the easiest way to produce a confidently wrong recommendation.

## 11. Outputs

```
trials.jsonl        every trial: point, bucket, metrics, status, diagnosis, artifacts
results.csv         flattened table
summary.md          plan, per-bucket / per-workload leaderboard, failure digest
best_by_bucket.*    kernel runs: one winner per shape, in the format the kernel
                    reads (e.g. E=128,N=768,...,dtype=fp8_w8a8.json for triton MoE)
best.yaml           deployment runs: `python -m sglang.launch_server --config best.yaml`
best.sh             rendered launch command
pareto.md           feasible frontier for vector objectives
logs/               per-trial server + benchmark logs
```

The reporter writes whatever the tuned layer consumes: `render_config()` on the
driver knows whether that is a `ServerArgs` YAML for `server_args_config_parser.py`
or a per-shape kernel config. Either way the result is deployable instead of
something a human retypes.

## 12. CLI

```bash
# inner layer: tune every kernel + dispatch heuristic this model uses at tp=8
python -m sglang.auto_tune --model-path Qwen/Qwen3-30B-A3B-Instruct-2507 --tp 8
python -m sglang.auto_tune --model-path ... --tp 4 --kernels moe_triton,allreduce

# outer layer: declarative deployment tuning
python -m sglang.autotune run      --config tune.yaml
python -m sglang.autotune plan     --config tune.yaml   # no GPUs touched
python -m sglang.autotune validate --config tune.yaml
python -m sglang.autotune report   --dir ./autotune/run
python -m sglang.autotune quickstart --model-path ... --gpu-count 8 --preset chat
```

`sglang.auto_tune` is a thin front: it derives the kernel list from the model
architecture, builds one `TuneTask` per kernel with the right space and bucket
rule, runs them serially, and writes each winner table. The CI workflow is this
command crossed with a model list and a runner list.

`plan` matters more than it looks: a tuning run is a multi-hour commitment, and
the user should be able to read what it intends to do before spending that.

## 15. Open questions

1. **Default strategy.** `coordinate` is predictable and explains itself; `asha`
   finds more but is harder to reason about. Proposal: `coordinate` when a
   non-trivial `space.fixed` baseline is supplied, `asha` otherwise.
2. **Where do tuned results live?** Per-run artifacts only, or a checked-in
   registry of known-good configs per (model, GPU, workload) that CI refreshes?
   The latter is the higher-value product but needs an ownership story.
3. **Measurement noise.** `steady_state` removes the ramp-up confound, but close
   candidates will still be separated by noise. Do we require a significance
   margin before declaring a winner, or re-measure only the top-k?
4. **Scope of `ServerArgs` introspection.** How much do we couple to argparse
   internals, given `server_args.py` is large and uses hook-based arg groups
   under `python/sglang/srt/arg_groups/`?
5. **Relationship to the removed tool's configs.** Prior cookbook YAMLs are
   recoverable from git history. Do we port a few as regression fixtures, or
   start the config corpus fresh?
6. **Multi-workload aggregation (follow-up).** `Objective.aggregate()` is the
   hook; the policy is undecided. Candidates: worst-case across workloads
   (robust, pessimistic), weighted sum with per-workload normalization, or a
   vector objective with one component per workload and a Pareto report.
   Related: `hardware.gpus_per_trial` is a run constant today, but `tp_size`
   / `dp_size` / `pp_size` are knobs, so slot sizing eventually has to be
   derived per point.
